# Size ceilings for the SHIPPED artifacts — checked by `zig build size -Doptimize=ReleaseSmall`.
#
# Format: <artifact-name> <ceiling-bytes>    (blank lines and `#` comments ignored)
#
# ⚠️ A ceiling is EXACT, not a budget with headroom. Any growth fails the build, which forces raising
# the number in the same commit that grows it — so every increase is a deliberate, reviewed act with a
# reason in the log. Headroom would let drift accumulate silently, which is precisely the failure this
# gate exists to prevent: between 2026-07-14 and 2026-08-11 the DLL grew +75% and the static lib +122%
# while "smallest binary" was a stated goal, because nothing measured them.
#
# Raising a ceiling is legitimate — features cost bytes. State WHAT bought the bytes in the commit
# message. Lowering one after a win is equally expected; re-run and commit the smaller number.
#
# Baseline measured 2026-08-11, Zig 0.16.0, x86_64-windows, ReleaseSmall:
#   wazmrt.exe  911,360    wazmrt.lib  279,444    wazmrt.dll  227,328
#
# NOTE: `wazmrt.lib` is the STATIC library only. `zig build dll` overwrites it with the DLL's much
# smaller import library, so measure the static lib from a plain `zig build`, never after `dll`.

# RAISED 2026-08-11 by the ABI-2 flip (`zig build` now installs src/capi.zig, not
# src/wasm_c_api.zig). What bought the bytes, and it is FEATURES, not waste:
#
#   dll  227,328 -> 845,312   (+618 KB, 3.7x)
#   lib  279,444 -> 973,600   (+694 KB, 3.5x)
#   exe  911,360 -> 911,872   (+512 B — features.zig, nothing structural)
#
# The old wasm-c-api surface could not assemble text, could not serve WASI, and needed no `Io`.
# The new one does all three, so the embed artifact now contains `wat.zig` + `sexpr.zig` (for
# wazmrt_module_new_wat / wazmrt_wat_to_wasm), `wasi.zig` (for wazmrt_linker_define_wasi) and
# `std.Io.Threaded`. This is not an apples-to-apples comparison with the old number and must not
# be quoted as a regression — but it IS a real cost against the smallest-binary goal.
#
# ⚠️ THIS IS THE MEASUREMENT THAT MAKES TRACK 2c (comptime feature gating) NECESSARY RATHER THAN
# NICE. `.wat` is not being descoped — owner, 2026-08-11 — but an embedder who never assembles
# text should not have to carry the assembler. `-Dwat=false` / `-Dwasi=false` build flags are the
# recorded compromise; until they exist, every FFI consumer pays for both.

# RAISED 2026-08-13 (R2). Measured ReleaseSmall, Zig 0.16.0, x86_64-windows, static lib from a
# PLAIN `zig build` (never after `zig build dll`).
#
#   artifact     ceiling was    at 3dd41a0 (pre-R2)    after R2      R2's share
#   wazmrt.exe       911,872               933,888      939,008          +5,120
#   wazmrt.lib       973,600               998,228      999,296          +1,068
#   wazmrt.dll       845,312               864,768      864,768               0
#
# ⚠️ MOST OF THIS OVERSHOOT IS NOT R2's. The ceilings were ALREADY breached at 3dd41a0 — exe
# +22,016, lib +24,628, dll +19,456 — by the R1/typematch commits of 2026-08-12, which grew the
# artifacts without running `zig build size`. R2 is charged +5,120 exe / +1,068 lib / +0 dll, and
# the rest is drift that this gate was built to catch and did not, because nothing RAN it. The
# gate works; the workflow around it did not. **A gate only gates the commits that run it** — the
# lesson is the same shape as "a goal with no gate is a preference", one level up.
#
# What bought R2's bytes: `interp.Store` (funcref resolution + the orphan list), `Instance.Global`
# as a shared cell, per-instance `tag_ids`, the §5.5.6 typed-table decode path, and `wast.zig`'s
# `module definition`/`instance` commands. The DLL is byte-identical because none of it is
# reachable from the C ABI surface's own code paths — it is all in code the DLL already carried.

# RAISED 2026-08-13 (R3 — the six GC array bulk ops). Measured ReleaseSmall, Zig 0.16.0,
# x86_64-windows, static lib from a PLAIN `zig build` (never after `zig build dll`).
#
#   artifact     ceiling was    at 6291038 (pre-R3)    after R3      R3's share
#   wazmrt.exe       939,008               939,008      945,152          +6,144
#   wazmrt.lib       999,296               999,186    1,007,444          +8,258
#   wazmrt.dll       864,768               864,768      871,936          +7,168
#
# ✅ Unlike R2, ALL of this overshoot is R3's: the pre-R3 commit measures at (exe, dll) or just
# under (lib, −110) its ceiling, so nothing was inherited. That is what the previous entry's
# workflow lesson bought — HEAD was measured in a worktree before the ceilings were touched, not
# assumed.
#
# ⚠️ The DLL is +7,168 here, and the R2 entry above recorded +0. That is not drift — it is the
# first entry whose code the C ABI actually reaches: `array.new_data`/`new_elem`/`fill`/`copy`/
# `init_data`/`init_elem` are decoder, validator AND interpreter arms, all of which any embedder
# running a GC module executes. R2's Store/linking work was reachable only from paths the DLL
# already carried, which is why it cost nothing there.
#
# What bought the bytes: six `Op` tags with three new `Imm` shapes (`gc_data`/`gc_elem`/
# `gc_array_copy`) threaded through `decodeBody`, `immediateKind`, `emitInstr`, `checkStaticIndices`,
# `FuncValidator.step` and the interpreter dispatch switch — plus `fieldByteSize`/`fieldFromBytes`
# for the little-endian data-segment decode. Six instructions across six files is the honest price
# of a proposal piece that was missing rather than merely unoptimised.
